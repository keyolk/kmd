# kmd 효용성 평가 (evaluation)

"kmd가 정말 쓸모 있나"를 재현 가능한 숫자로 답하기 위한 평가 하니스.
검색이 뭔가 찾았다(L1)를 넘어, 주입이 답변에 쓰였나(L2)까지 잰다.

| 층위 | 질문 | 커맨드 | 판정 방식 |
|---|---|---|---|
| **L1 검색 품질** | 관련 문서를 찾았나? | `kmd eval` | 자동 (known-item / gold) |
| **L2 주입 효용** | 답변이 주입 컨텍스트를 썼나? | `kmd util` | 자동 (transcript 오버랩) |

> L3(kmd 답이 qmd보다 나았나 — `kmd ab`)는 qmd를 이 환경에서 제거하면서 함께 삭제했다.
> 아래 대조표는 두 엔진이 공존하던 시점의 기록이며 지금은 재현되지 않는다.

---

## L1 — 검색 품질 (`kmd eval`)

### known-item (자기지도, 라벨 불필요)

문서에서 한글이 가장 조밀한 라인을 뽑아 훅과 동일하게 키워드화한 뒤, 그 쿼리로
**원본 문서가 top-k에 돌아오는지** 본다. 라벨링이 필요 없고 수백 쿼리로 재현
가능하며, 한글 형태소 매칭을 격리해서 잰다.

```sh
make eval        # 한/영 혼합
make eval-ko     # 한글만
```

**현재 (400 쿼리, 지식 컬렉션, k=5):** 전체 R@5 81% (한글 75% · 영어 97%).

**과거 대조 (341 쿼리, qmd 공존 시점):**

| 구간 | 엔진 | R@1 | R@3 | R@5 | MRR | lat(ms) |
|---|---|---|---|---|---|---|
| 한글 | **kmd** | **44%** | **59%** | **69%** | **0.530** | 75 |
| 한글 | qmd | 30% | 41% | 44% | 0.355 | 141 |
| 영어 | **kmd** | **93%** | **97%** | **99%** | **0.957** | 53 |
| 영어 | qmd | 84% | 85% | 85% | 0.844 | 130 |

→ 한글 R@5 **+25%p**, 영어도 앞서고 지연은 절반.

> 당시 공정 비교를 위해 양쪽 경로를 동일 정규화해 매칭했다(qmd는 파일명 공백을
> 하이픈으로 바꿨다: `20260429 0` → `20260429-0`). 그 정규화는 지금도 `eval.rs`에
> 남아 있어, 옛 스킴으로 적힌 gold 파일이 계속 매칭된다.

### gold (수동 라벨 회귀)

`eval/gold.yaml`에 `prompt → expect_any(파일/제목 substring)`을 사람이 라벨.
**전 인덱스**에서 기대 문서가 top-k에 도달하는지(retrievability ceiling) 본다.

```sh
make eval-gold
```

이 모드는 실제 약점도 드러낸다: `exp` 컬렉션(25916 파일, 과거 워크트리·중복)이
`wiki`의 정제된 지식 문서를 밀어내, paraphrase 한글 질의의 회수율을 떨어뜨린다.
훅은 claude 컬렉션만 필터하므로 실사용엔 영향이 작지만, 인덱스 위생 이슈로 기록해 둔다.

## 엔진 대조 — BM25 vs 벡터 vs hybrid (`--compare`)

`kmd eval`은 기본적으로 BM25만 잰다. `--compare`는 같은 쿼리를 세 엔진에
돌려 나란히 출력한다. `--engine {bm25|vector|hybrid}`로 하나만 고를 수도 있다.

```sh
make eval-compare        # known-item 200 쿼리
make eval-compare-gold   # gold set
```

벡터/hybrid는 `embed` 피처가 필요하다(`make build-embed`). 임베딩은
`kmd embed`로 미리 채워야 하고, `--collection`으로 대상을 좁힐 수 있다 —
필터가 없으면 id가 가장 작은 `exp`(대상의 95%)가 먼저 처리되어 훅이 실제로
읽는 컬렉션이 맨 뒤로 밀린다.

### 대조에서 검색 범위를 좁히는 이유

단독 평가는 전 인덱스를 대상으로 한다(retrievability ceiling). `--compare`는
그러지 않고 **본문을 store에 저장하는 컬렉션**으로 범위를 좁힌다.

`project` 축(git 저장소 36만 건)은 `store_body: false`라서 임베딩 대상이 아니다.
범위를 그대로 두면 BM25만 그 36만 건과 경쟁하고 벡터는 경쟁 문서가 없는
모집단에서 검색한다. 그건 벡터가 더 잘 찾은 게 아니라 상대가 없었던 것이므로,
그 조건에서 나온 우열은 근거로 쓸 수 없다.

## 무엇을 재는 층위인가 — `--engine pipeline`

`bm25` / `vector` / `hybrid`는 **원시 검색 결과**를 잰다. 훅은 그 위에
`rag::filter_hits`를 얹는다: 컬렉션 범위 제한, 컬렉션 가중 재정렬, L0 커버
learnings 제외, 상위 3건 절단.

`--engine pipeline`은 그 전체를 잰다 — 훅이 실제로 주입하는 것이다. 이 모드가
없으면 `filter_hits`의 어떤 변경도 측정할 수 없다. 실제로 컬렉션 가중을
1.0에서 5.0까지 바꿔도 gold 점수가 한 자리도 안 움직였는데, 원인은 가중이
무효인 것도 있었지만 **eval이 그 코드를 아예 지나가지 않았던 것**이 먼저였다.

pipeline은 원본 프롬프트를 받는다(다른 엔진은 호출부가 추출한 키워드를 받는다).
`run_pipeline`이 게이트와 키워드 추출을 스스로 하므로, 추출된 쿼리를 넘기면
그것이 다시 게이트에 들어가 `too_short`로 걸린다. 이 실수로 gold 55건 중 16%만
통과한 채로 측정한 적이 있다.

`--compare`에는 pipeline이 빠져 있다. 층위가 달라서 한 표에 놓으면 엔진 비교로
오독된다.

### 측정된 사실: 컬렉션 가중은 이 코퍼스에서 실효가 없다

`KMD_CURATED_WEIGHT`를 1.0~5.0으로 스윕해도 gold 55케이스 정답률이 31%로
고정이다. 주입 결과 자체는 7건에서 바뀌지만(learnings 하나가 skills로 교체되는
식) 그 교체가 정답 판정을 넘나들지 않는다 — 상위 3건 안에서 순서만 섞인다.

그래도 배분 문제는 실재한다. `kmd util`의 컬렉션별 기여도를 보면 정제 지식은
주입 파일의 10%인데 활용된 프롬프트의 31%에 기여한다(skills 6%→15%,
memory 3%→12%, rules 1%→4%). 코퍼스가 learnings 1,431건 대 정제 지식 98건이라
가중 1.3배로는 15배 규모 차이를 이기지 못한다. 고치려면 가중이 아니라 검색
자체가 정답을 3건 안에 넣어야 한다.

---

## 측정된 천장 — 주입 창은 병목이 아니었다

`KMD_MAX_RESULTS`(훅이 주입하는 히트 수)를 3에서 30까지 키우며 gold 정답률을
쟀다. 44%에서 멈춘다 — 30건까지 열어도 55케이스 중 31건은 정답이 후보에
**아예 없다.** 재정렬로도, 창 크기로도 넘을 수 없는 선이다.

이것이 컬렉션 가중이 무효였던 진짜 이유다. 정답이 창 밖에 있으면 곱셈으로
끌어올 수 없다.

미스 31건을 분해하니 게이트 차단 9건 + 검색 실패 22건이었고, 둘 다 한국어
처리 버그였다:

- **게이트**: `MIN_PROMPT_LENGTH = 20`을 한국어에도 적용했다. "노드가 안
  뜨는데 어디를 봐야 하지"는 19자로 차단되는데, 대응하는 영어 질문은 50자다.
  실사용에서 `too_short`로 막힌 한국어 프롬프트 1,599건 중 303건(고유)이
  15~19자이고 그중 88건이 질문형이다. 한글 임계값을 15자로 낮췄다.
- **키워드 추출**: `chars().count() > 2` 필터가 한국어 2글자 내용어를 버렸다.
  "버그 찾기 전에 먼저 확인해야 할 게 있었는데" → **"확인해야 있었는데"**로,
  문서를 특정하는 "버그"와 "찾기"가 정확히 사라진다.

두 수정 합계로 gold 정답률이 **31% → 42%** (`MAX_RESULTS=3`, 훅 실제 출력
기준). 회귀 테스트가 둘 다 고정한다 — 되돌아가면 훅이 에러 없이 조용히
아무것도 주입하지 않으므로 눈에 띄지 않는다.

## L2 — 주입 채택률 (`kmd util`)

`rag.jsonl`(주입 기록)과 Claude Code transcript(실제 답변)를 세션+프롬프트로 조인해,
**답변이 주입 컨텍스트의 토큰을 유의하게 재사용했는지** 오버랩으로 근사한다.
프롬프트에 이미 있던 토큰은 신호에서 제외(주입 기여분만 카운트).

```sh
make util
```

정밀도를 위해 `rag.jsonl`의 각 히트에 `snippet`을 남기도록 로깅을 확장했다
(과거 로그는 snippet이 없어 쿼리 토큰으로 폴백 → 채택률이 낮게 근사됨).
snippet 로깅이 쌓인 뒤의 수치가 실효 채택률이다.

지표: 주입 엔트리 / 답변 매칭 / 활용됨(≥15% overlap) / 평균 오버랩 / 한글 분리 /
**컬렉션별 주입 분해**(무엇이 증강되나).

### 무엇이 증강되나 — `kmd util`의 컬렉션 분해

실측(실사용 511건): 주입 파일의 **97%가 `learnings`(과거 세션 로그)**, 정제된
지식(memory/skills/agents)은 4%뿐. 그래서 토큰 오버랩 채택률이 8%로 낮은 것은
버그가 아니라 실제 신호다 — 세션 로그는 답변에 문자 그대로 재사용되기보다
배경 참고로 쓰이므로 오버랩으로는 태생적으로 안 잡힌다.

### 실사용 세션 드릴다운 — `kmd show`

집계가 아니라 "어느 세션의 어떤 프롬프트에 무엇이 증강됐고, 답변이 그걸 썼나"를
눈으로 훑는다. 실사용(uuid) 세션만, 자동 프롬프트(`<task-notification>` 등)와
중복은 걸러낸다.

```sh
kmd show            # 최근 실사용 20건
kmd show <sid>      # 특정 세션 prefix
kmd show --all      # 합성/자동 프롬프트까지 포함
```

각 줄: `[KO/en] 프롬프트  활용마크(✓ 활용 N% / · 답변있음 N% / 답변 미발견)`,
그 아래 추출 쿼리와 증강된 파일 목록.

> transcript 조인은 프롬프트 이후 **다음 사용자 프롬프트 전까지의 assistant 텍스트
> 전체**(그 턴의 답변 전부)를 모은다. 첫 서두만 잡으면 오버랩이 0에 수렴한다.

## 한 번에

make eval-all    # L1 + L2
