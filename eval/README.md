# kmd 효용성 평가 (evaluation)

"kmd가 정말 쓸모 있나"를 재현 가능한 숫자로 답하기 위한 3층 평가 하니스.
검색이 뭔가 찾았다(L1)를 넘어, 주입이 답변에 쓰였나(L2), 그래서 답이 더 나았나(L3)까지 잰다.

| 층위 | 질문 | 커맨드 | 판정 방식 |
|---|---|---|---|
| **L1 검색 품질** | 관련 문서를 찾았나? | `kmd eval` | 자동 (known-item / gold) |
| **L2 주입 효용** | 답변이 주입 컨텍스트를 썼나? | `kmd util` | 자동 (transcript 오버랩) |
| **L3 최종 효용** | kmd 답이 qmd보다 나았나? | `kmd ab` | 프록시 + 외부 블라인드 |

---

## L1 — 검색 품질 (`kmd eval`)

### known-item (자기지도, 라벨 불필요)

문서에서 한글이 가장 조밀한 라인을 뽑아 훅과 동일하게 키워드화한 뒤, 그 쿼리로
**원본 문서가 top-k에 돌아오는지** 본다. 라벨링이 필요 없고 수백 쿼리로 재현
가능하며, 한글 형태소 매칭을 격리해서 잰다. `--compare-qmd`로 qmd와 나란히 대조.

```sh
make eval        # 한/영 혼합, kmd vs qmd
make eval-ko     # 한글만
```

**실측 (341 쿼리, 지식 컬렉션, k=5):**

| 구간 | 엔진 | R@1 | R@3 | R@5 | MRR | lat(ms) |
|---|---|---|---|---|---|---|
| 한글 | **kmd** | **44%** | **59%** | **69%** | **0.530** | 75 |
| 한글 | qmd | 30% | 41% | 44% | 0.355 | 141 |
| 영어 | **kmd** | **93%** | **97%** | **99%** | **0.957** | 53 |
| 영어 | qmd | 84% | 85% | 85% | 0.844 | 130 |

→ 한글 R@5 **+25%p**, 영어도 앞서고 지연은 절반.

> ⚠️ 공정 비교 주의: qmd는 파일명 공백을 하이픈으로 정규화한다
> (`20260429 0` → `20260429-0`). eval은 양쪽 경로를 동일 정규화해 매칭한다.
> 이 정규화를 빼면 qmd가 실제로 찾은 문서도 미스로 집계돼 qmd 0%라는 가짜 결과가 나온다.

### gold (수동 라벨 회귀)

`eval/gold.yaml`에 `prompt → expect_any(파일/제목 substring)`을 사람이 라벨.
**전 인덱스**에서 기대 문서가 top-k에 도달하는지(retrievability ceiling) 본다.

```sh
make eval-gold
```

이 모드는 실제 약점도 드러낸다: `exp` 컬렉션(25916 파일, 과거 워크트리·중복)이
`wiki`의 정제된 지식 문서를 밀어내, paraphrase 한글 질의의 회수율을 떨어뜨린다.
훅은 claude 컬렉션만 필터하므로 실사용엔 영향이 작지만, 인덱스 위생 이슈로 기록해 둔다.

## L2 — 주입 채택률 (`kmd util`)

`rag.jsonl`(주입 기록)과 Claude Code transcript(실제 답변)를 세션+프롬프트로 조인해,
**답변이 주입 컨텍스트의 토큰을 유의하게 재사용했는지** 오버랩으로 근사한다.
프롬프트에 이미 있던 토큰은 신호에서 제외(주입 기여분만 카운트).

```sh
make util
```

정밀도를 위해 `rag.jsonl`의 각 히트에 `snippet`을 남기도록 로깅을 확장했다
(과거 로그는 snippet이 없어 쿼리 토큰으로 폴백 → 채택률이 낮게 근사됨).
snippet 로깅이 쌓인 뒤의 수치가 실효 채택률이다.

지표: 주입 엔트리 / 답변 매칭 / 활용됨(≥15% overlap) / 평균 오버랩 / 한글 분리.

## L3 — A/B 블라인드 비교 (`kmd ab`)

같은 프롬프트(`eval/prompts.txt`)에 kmd·qmd가 각각 주입할 컨텍스트를 만들고
A/B를 결정적으로 스왑해 블라인드 페어를 생성한다.

```sh
make ab          # 내장 프록시 판정 (프롬프트 키워드 커버리지)
make ab-emit     # 블라인드 페어 → eval/pairs.jsonl (+ .key.jsonl)
```

### 외부 블라인드 판정 왕복

`ab-emit`이 내는 `pairs.jsonl`엔 엔진 라벨이 없다(진짜 블라인드).
LLM/사람이 각 페어를 보고 `{"id":N,"winner":"A"|"B"|"tie"}` 형식으로 판정하면,
`.key.jsonl`의 A/B↔엔진 매핑으로 취합한다:

```sh
kmd ab --judge verdicts.jsonl --prompts eval/pairs.jsonl
```

**실측 (12 프롬프트):**

- 내장 프록시: kmd 승 50% · qmd 승 40% · tie 10%,
  **컨텍스트 제공률 kmd 10/10 vs qmd 7/10** (qmd는 한글 질의 3건에서 아무것도 주입 못 함)
- 실제 블라인드 판정(10 페어): **kmd 승 70% · qmd 승 30%**

프록시(키워드 커버리지)로는 안 잡히는 품질 차이가 블라인드 판정에서 드러난다:
kmd는 정제된 지식 문서(agent/skill/memory 정의, o11y 레퍼런스 표)를 주입하는 반면,
qmd는 같은 질의에서 과거 세션 로그를 주입하는 경향. 최종 판정은 항상 블라인드로 확정하라.
